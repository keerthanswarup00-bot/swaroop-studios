## 1. Executive Summary

Swaroop Studios is a single-document static site with one small Vercel serverless
API. The craft in it is genuinely good: no horizontal overflow at any of eleven
tested widths, all five routes return 200, per-route titles/descriptions/canonicals
are correct and dynamic, all 8 videos are correctly encoded with fast-start and no
audio, all 389 image files exist on disk, every text/background colour pair tested
passes WCAG AA, the About archive slideshow added at HEAD is fully correct, and the
admin API rejects every unauthenticated mutation.

The audit found **32 findings: no P0, three P1, seven P2, twelve P3 and ten P4.**
The serious ones are all about **how much data the site asks for before the visitor
has done anything**:

1. **A first homepage visit downloads 57.6 MB on a 390 px phone and 95.5 MB on a
   1440 px desktop without a single scroll.** A 46.8 MB reception film sits ~4,900 px
   below the fold, loads and *plays*. This is a regression: `syncEditorialVideos()`
   bypasses the `IntersectionObserver` that exists for exactly this purpose.
2. **WebKit can reach 125.9 MB on that same phone viewport**, re-requesting the same
   film and eventually falling back to the 1080p source on a 390 px screen.
3. **The gallery has no responsive images at all.** 55 of 55 images have no `srcset`,
   so a 163 px-wide tile downloads an 812 KB JPEG — while a 36 KB AVIF of the same
   frame already exists on disk. `/gallery` costs 16.6 MB on first load.

Behind those: a desktop **CLS of 0.40–0.50** (poor) caused by `.page{display:none}`,
an enquiry form that **stores nothing** yet always confirms receipt, an admin API
that reads from a **stale deploy-time snapshot** and can silently clobber newer
remote data, and a missing set of security headers.

The three P1s are cheap to fix — the video one is essentially deleting five lines
that reintroduce an earlier bug, and the gallery one is changing `useAvif:false` to
`true`. Both are called out in the fix order in §20.

**Recommended order:** F-01 → F-02 → F-03 → F-04 → F-06 → F-07 → F-05.

## 2. Project Overview

The marketing site for a photography studio in Bengaluru operating since 1972. It
presents six client-side views (Home, About, Services, Gallery, Contact, Admin), a
curated local image archive, four silent cinematic video bands, a five-frame About
archive slideshow, and a self-service gallery admin backed by the GitHub Contents API.

**Routing model.** There is one HTML document. Navigation is hash-based (`#/gallery`),
with Vercel rewrites mapping the six clean paths (`/`, `/about`, `/services`,
`/gallery`, `/contact`, `/admin`) onto that same document. `render_route()` at
line 1367 resolves the hash first, then the pathname.

**Content model.** Photographs come from two places that are merged client-side:
70 entries in the inlined `LOCAL_IMAGES` map, and 37 records served from
`/api/gallery` (which reads `data/gallery.json`). The rendered gallery has 55 items.

## 5. Code Quality & Maintainability

**Confirmed.** The single-file architecture is the dominant maintainability risk:
2,727 lines in one document means CSS, markup, five route views, six videos, the
gallery, the lightbox, the admin panel and the router all share one file, so any
edit risks an unrelated regression and no module boundary exists.

Specific, confirmed issues:

- **Dead feature block.** `#filmSection` (line 840) carries an inline
  `style="display:none"`, and `loadFilm()` (~2314) is the only code that could ever
  reveal it. Because the reveal path requires `dbCap` (F-14), the section and its
  `#videoModal` / `openVideo()` / `vmVideo` companions are **permanently
  unreachable**. Confirmed at runtime: `getComputedStyle(#filmSection).display === "none"`.
- **Dead CSS.** `.film-section`, `.film-frame`, `.film-cap`, `.film-tag`, `.play-btn`,
  `.film-grid` and `#videoModal` rules (~15 blocks) ship for markup that can never
  render.
- **Duplicated inline handlers.** All five `#mobileNav` links (lines 740–744) repeat
  the same 120-character `onclick` string to close the menu and reset
  `aria-expanded`. A single delegated listener would do.
- **`render_route` is called from many places** (`syncEditorialVideos` is invoked at
  1607, 2258 and 2343), so a route change fans out into video sync, gallery
  re-render, SEO updates and observer teardown with no single orchestration point.
- **Positive.** Functions are small and named, `safeEqual`/`slug`/`json` are tidy
  helpers, comments explain *why* (e.g. the recursive-`setTimeout` rationale at
  1950–1951), and the About slideshow's state machine is clearly commented.

### 9.2 Loading and autoplay — two confirmed defects

**F-01 · P1 · Confirmed — the IntersectionObserver is bypassed and every video on the
active view downloads and plays before any scroll.**

Root cause, `syncEditorialVideos()` at line 1517:

```js
const canPlay = !section.hidden && editorialSectionIsActive(section)
             && !document.hidden && !prefersReducedMotion()
             && video.dataset.userPaused !== "true";   // ← no viewport test
if (canPlay) { loadEditorialVideo(video); retryEditorialVideo(video); }
```

`canPlay` never asks whether the section is near the viewport. `loadEditorialVideo`
sets `video.preload="metadata"` (1471), assigns `video.src` (1477) and calls
`video.load()` (1479); `retryEditorialVideo` then calls `playEditorialVideo`, which
calls `video.play()` (1496). So every `[data-video-section]` on the active view
streams immediately. The observer at line 1571 (correctly configured with
`rootMargin:"240px"`) becomes redundant — and is called separately, so the lazy
path can never win.

`syncEditorialVideos()` runs from `initEditorialVideos()` (1607) and from route
render (2258, 2343), so this happens on first paint and on every navigation.

Measured, 14 s after load, **with no scrolling at all**:

| Condition | Total transferred | `intro-band` | `reception-film` | Off-screen playback |
|---|---|---|---|---|
| iPhone 390 (WebKit) | **57.4 MB** | 9.5 MB (2 req) | 46.8 MB (2 req) | hero at `rectTop=904` playing |
| Chrome mobile 390 | **57.6 MB** | 9.5 MB (1 req) | 46.8 MB (1 req) | reception at `rectTop=4882` **`playing=true`, ct=14.1 s** |
| Chrome desktop 1440 | **95.5 MB** | 20.1 MB | 69.6 MB | reception at `rectTop=4274` **`playing=true`, ct=15.1 s** |

Note the desktop hero band at `rectTop≈900` on a 900 px-tall viewport is itself
below the fold on many laptops, and still plays.

**`shouldConserveVideoData()` (line 1415) is defined but never called from the video
path.** Its only call site is `autoplayBlocked()` at line 1948, which belongs to the
About slideshow. So a Save-Data or 2G visitor is served the full 57–126 MB — the
exact users the function was written for. Confirmed by reading all call sites.

*Recommended fix:* delete the `loadEditorialVideo(video); retryEditorialVideo(video);`
pair from `syncEditorialVideos()` (leave the `pause()` and `updateEditorialVideoButton`
branches), and add `!shouldConserveVideoData()` to the `canPlay` guard plus the
`IntersectionObserver` branch so data-saver users are honoured.

**F-02 · P1 · Confirmed — WebKit retries without backoff and can upgrade a phone to
the 1080p source.**

`recoverEditorialVideo` (1431) is bound to each video's `error` event (1471) with no
attempt counter and no delay, and it re-runs the same mobile/desktop selection. On a
390 px WebKit viewport the harness observed `reception-film-720p.mp4` requested
**5 times, 125.9 MB total**, after which the element's `src` was
`reception-film-1080p.mp4` (69.6 MB, 1920×1080) on a 390 px screen.

*Recommended fix:* cap recovery attempts (e.g. a counter in `dataset`), add
exponential backoff, and never re-select a larger source than the original attempt
once a 720p load has failed.

## 10. Image & Asset Optimization

**Integrity — all pass.** 389 files, **100,854,377 B (96.2 MB)** in
`assets/images`. All 70 `LOCAL_IMAGES` entries resolve: every expected AVIF
(480/768/1200/1800/2400 px) and JPEG fallback exists, and there are **no orphan
image basenames**. Total `assets/` = **412,658,318 B (393.5 MB)**, of which videos
are 296.6 MB.

One non-responsive file: `studio-story-replacement.svg` (12,634 B), an SVG
placeholder.

**F-03 · P1 · Confirmed — the gallery has no responsive images.**

`galleryItemImage()` at line 1846:

```js
return localImageMarkup(image,{sizes,useAvif:false});
//                            ^^^^^^               ^^^^^^^^^^^
//                    ignored without srcset      AVIF disabled
```

Measured on `/gallery`: **`noSrcset: 55, totalImgs: 55`** — every single image has
no `srcset`, so the browser can only pick the largest JPEG, and the `sizes`
attribute is inert without a `srcset`. It stays that way with `/api/gallery`
blocked, so it is not a data problem.

The waste is severe. At a 375 px viewport the first tile is **163 px wide** and
downloads `06-1800.jpg` = **812,334 B**, while `06-480.avif` = **35,811 B** exists —
a **22.7×** over-fetch. Other examples: `07-1800.jpg` 1,080,313 B; `4-1080.jpg`
186,417 B; `3-1080.jpg` 130,018 B.

Route cost, first load, no scrolling:

| Route | Transferred | Responses |
|---|---|---|
| `/` | 5.77 MB | 19 |
| `/about` | 1.28 MB | 16 |
| `/services` | 1.37 MB | 17 |
| `/gallery` | **16.63 MB** | 40 |

*Recommended fix:* change `useAvif:false` to `true` in `galleryItemImage` (one
token) and confirm `localImageMarkup` emits `srcset`/`sizes` when asked. The
non-gallery `<picture>` paths are already correct — the About slideshow proved it.

**F-08 · P2 · Confirmed — hidden views eagerly fetch their media.**

`.page{display:none}` (193) hides five views, but the hero and poster `<img>`/`<video>`
elements inside them are still parsed and fetched. On `/about` with no scrolling,
the browser downloaded `dsc05478-1800.avif` plus the wedding, studio and reception
posters belonging to the hidden home and services views.

*Recommended fix:* set `loading="lazy"` on below-fold hero/poster imagery, or have
`render_route` set `src`/`poster` only for the active view.

**Correctly implemented (for contrast):** every non-gallery `<picture>` emits AVIF +
JPEG with `srcset` and `sizes`; the videos use `data-desktop-src`/`data-mobile-src`;
`loading="lazy"` and `decoding="async"` are used on gallery images; all videos have
explicit `width`/`height`, preventing layout shift.

`api/gallery.js` is 45 lines. Verified behaviour against production:

| Request | Result | Notes |
|---|---|---|
| `GET /api/gallery` | 200, 3,409 B | Returns the public dataset |
| `GET /api/gallery?action=session` | 200 | `{"ok":true,"authenticated":false,"configured":true}` |

| `GET ?action=admin` / `bootstrap` / `messages` unauth | 200 | Returns the *public* dataset only — no leak |
| 13 MB POST body | 413 | Platform guard fires before the handler |
| `GET /api/nonexistent` | 404 | Vercel default page |

**Confirmed passes.** Every mutating action is correctly gated behind
`isAuthed` (line 39). `safeEqual` (18) uses `crypto.timingSafeEqual`. The session
cookie is `HttpOnly; Secure; SameSite=Strict; Max-Age=28800` (27). No `Set-Cookie`
on a failed login. The API sends **no** `Access-Control-Allow-Origin`, and `OPTIONS`
returns 204 with no CORS headers, so cross-origin reads fail preflight — correct.

**F-06 · P2 · Confirmed — the API reads a stale deploy-time snapshot and can
overwrite newer remote data.**

`readGalleryData()` (line 24) tries `fs.readFileSync(path.join(process.cwd(), DATA_PATH))`
**first** and only falls back to the GitHub API if that throws. On Vercel,
`process.cwd()` is the deployment bundle, which *contains* `data/gallery.json`, so
the read always succeeds and always returns the **snapshot frozen at deploy time**.
Confirmed: production `/api/gallery` returned exactly the 37 records in the tracked
`data/gallery.json`, byte-for-byte in id order.

`writeGalleryData()` (25) fetches a fresh `sha` from GitHub — so no 409 conflict —
but then PUTs the *stale* content. Two admin edits made before the next redeploy
therefore produce last-write-wins over a snapshot that may be missing images added
in between. This is the only confirmed data-loss path in the codebase.

*Recommended fix:* read from GitHub when `process.env.VERCEL` is set (or drop the
filesystem read entirely for the write path), and return the post-write state.

**F-10 · P2 · Confirmed — no rate limiting or lockout on admin login.**

Six consecutive `POST ?action=login` requests with wrong passwords returned 401
each time: no `429`, no lockout, no backoff, no delay, and nothing rate-limited at
the platform. Combined with a guessable `ADMIN_PASSWORD`, this permits unlimited
online brute force. (The password itself is not in the repo — see §15 — so this is
the remaining exposure on the admin surface.)

*Recommended fix:* add Vercel WAF / rate-limit on `/api/gallery`, plus a per-IP
counter in the handler, and a short delay on failure.

**Also noted.** `readGalleryData`'s `catch{}` (24) swallows *every* error —
permission, parse and network alike — so a corrupt `data/gallery.json` fails
silently into a GitHub fallback. `body()` (29) accepts up to 12 MB while
`MAX_UPLOAD_BYTES` is 8 MB (12), an inconsistency the 8 MB check masks. The upload
MIME type is client-supplied and matched by regex only (42) with no content
sniffing — low risk because it requires authentication.

## What Was NOT Verified

Stated plainly so the report is not over-read:

- **Real devices.** Everything browser-based is Playwright 1.63.0 **Chromium and
  WebKit** on desktop. No physical iPhone, iPad, Android device, macOS Safari,
  Chrome, Firefox or Samsung Internet. WebKit is not Safari: iOS low-power-mode
  autoplay rules, memory limits and background suspension were not exercised.
- **Network shaping.** No throttled 3G/2G, high-LATency or packet-loss run. The
  57.6 MB mobile finding would be dramatically worse under throttling; that was not
  quantified.
- **Field data.** No real-user Core Web Vitals, CrUX, RUM or field LCP/INP/CLS.
  All CWV figures here are single synthetic runs.
- **Admin authenticated flows.** No admin password was used, so login success,
  upload, category editing, deletion, image cropping, film admin and the enquiries
  panel were **not** exercised end-to-end. F-06 and F-14 are derived from reading
  `api/gallery.js` and the client code, and are Confirmed by code inspection rather
  than by triggering the writes.
- **Screen readers and WCAG.** No NVDA/VoiceOver pass, no axe or Lighthouse run, no
  200% zoom, no `prefers-contrast`, no keyboard-only pass through the lightbox and
  admin panel. Contrast was computed for 15 curated pairs, not measured across every
  rendered state.
- **Video playback quality.** Codec, fast-start, dimensions and audio track count
  were verified; visual quality, frame pacing, colour rendition and playback on
  low-end hardware were not.
- **Vercel configuration.** Environment variable *names* were confirmed via
  `configured:true` and `.env.example`; **no environment value was read**. Project
  settings, domains, firewall/WAF rules, build logs and preview deployments were not
  enumerated.
- **Backups, monitoring, analytics, uptime and alerting.** None present in the repo
  and none audited.
- **Git history forensics** beyond a secret-pattern scan of all 715 objects, the
  unmerged remote branch, and author metadata.
- **The prior report's claims** were not re-litigated finding-by-finding; several of
  its P0/P1 items (gallery keyboard access, `/admin` navigation lock, reduced-motion
  video gating) were spot-checked and are now **fixed** — see §21.
